# ADR-0002: ใช้ event เพื่อแยกงานหลังการสั่งซื้อ

- **Status:** Proposed
- **Date:** 2026-10-27
- **Deciders:** ยังไม่ระบุ ดู Open questions

## Context and problem

หลักฐานของ ADR นี้มีเพียง R-12 ในข้อความนักศึกษา ไม่มีไฟล์ context และไม่ได้ตรวจสอบโค้ด การออกแบบด้านล่างเป็นข้อเสนอ ยังไม่ใช่คำอธิบายระบบปัจจุบัน

| หลักฐาน | ข้อกำหนด |
|---|---|
| R-12 ข้อ 1 ในข้อความนักศึกษา | หลังสั่งซื้อ ต้องส่งอีเมลยืนยันผ่าน MailFast ซึ่งเป็นผู้ให้บริการภายนอก แทน mock logic ของ emailservice |
| R-12 ข้อ 2 ในข้อความนักศึกษา | ต้องให้ loyalty points ผ่าน loyaltyservice ที่จะสร้างใหม่ |
| R-12 ข้อ 3 ในข้อความนักศึกษา | ต้องบันทึก analytics event ว่า “order placed” ให้ทีมการตลาด |
| R-12 ย่อหน้าสุดท้ายในข้อความนักศึกษา | ทีมการตลาดคาดว่าจะเพิ่ม SMS, fraud scoring และการอัปเดต recommendations ในปีหน้า |

ต้องเลือกวิธีประสานงานที่รองรับการเพิ่มงาน โดยข้อกำหนดยังไม่ระบุเวลาที่ต้องทำเสร็จ ลำดับงาน และนโยบายเมื่อเกิดความล้มเหลว

โครงสร้างการเรียกบริการปัจจุบัน protocol, data store, message broker และ API ของ MailFast: **Not evidenced in the provided files** จึงไม่อ้างว่ามีองค์ประกอบเหล่านี้อยู่แล้ว

## Decision drivers

ลำดับความสำคัญต่อไปนี้เป็นข้อเสนอที่ต้องยืนยันกับผู้รับผิดชอบ:

- **Modifiability:** เพิ่มงานหลังสั่งซื้อโดยจำกัดการแก้ส่วนรับคำสั่งซื้อ ตามทิศทางใน R-12 ย่อหน้าสุดท้าย
- **Reliability:** ติดตามและกู้คืนงานทั้งสามให้ครบตาม R-12 ข้อ 1–3
- **Availability / performance:** [Inferred] ความล่าช้าหรือความล้มเหลวของงานหนึ่งควรจำกัดผลกระทบต่องานอื่นและการตอบรับคำสั่งซื้อ
- **Cost / operability:** [Inferred] ความซับซ้อนในการดูแลระบบต้องคุ้มกับความยืดหยุ่นที่เพิ่มขึ้น

## Considered options

1. ให้ส่วนรับคำสั่งซื้อเรียก emailservice ที่เชื่อม MailFast, loyaltyservice และส่วนบันทึก analytics แบบ synchronous
2. เพิ่มตัวประสานงานแบบ asynchronous ที่เก็บสถานะและสั่งงานแต่ละขั้น
3. กระจาย OrderPlaced ผ่าน message broker แบบ durable ให้ตัวประมวลผลแต่ละงานรับแยกกัน

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| 1 — เรียกแบบ synchronous | โครงสร้างเริ่มต้นเรียบง่าย; ผู้เรียกทราบผลของแต่ละการเรียกทันที | [Inferred] latency และความพร้อมใช้งานของปลายทางกระทบการตอบรับคำสั่งซื้อ; เพิ่มงานต้องแก้ส่วนประสานงาน; เมื่อสำเร็จบางงานยังต้องจัดการ retry และงานซ้ำ |
| 2 — ตัวประสานงานแบบ asynchronous | แสดงสถานะรวมและควบคุมลำดับ เงื่อนไข และ retry ได้ชัดเจน | เพิ่มบริการและที่เก็บสถานะ; เพิ่มงานมักต้องแก้ workflow กลาง; ต้องดูแลความพร้อมใช้งานของตัวประสานงาน |
| 3 — กระจาย event | เพิ่มผู้รับใหม่ได้โดยไม่เพิ่มการเรียกในส่วนรับคำสั่งซื้อเมื่อข้อมูล event เพียงพอ; แยก retry และการปรับกำลังประมวลผลแต่ละงาน | เพิ่ม broker และงานดูแลระบบ; ผลสำเร็จเกิดภายหลัง; ต้องจัดการ event สูญหาย งานซ้ำ และการติดตามข้ามบริการ |

## Decision

เลือก **ตัวเลือก 3** เป็นข้อเสนอ โดยให้น้ำหนักกับการเพิ่มงานตาม R-12 ย่อหน้าสุดท้าย

**[Assumption]** งานทั้งสามยอมให้เสร็จภายหลังและทำงานแยกกันได้ ต้องยืนยันก่อนรับรอง ADR เพราะ R-12 ไม่ได้ระบุเรื่องลำดับและเวลาตอบรับคำสั่งซื้อ หากต้องมีลำดับหรือเงื่อนไขข้ามงานที่ซับซ้อน ให้ประเมินตัวเลือก 2 อีกครั้ง

เสนอการทำงานดังนี้:

1. เมื่อยอมรับคำสั่งซื้อสำเร็จ ให้สร้าง OrderPlaced ที่มี event_id, order_id, รุ่น schema และข้อมูลที่แต่ละงานจำเป็นต้องใช้ การตอบรับหมายถึงยอมรับคำสั่งซื้อแล้ว ยังไม่ใช่งานหลังสั่งซื้อเสร็จครบ
2. บันทึกคำสั่งซื้อและหลักฐานสำหรับส่ง event แบบ atomic เสนอใช้ transactional outbox หาก data store รองรับ transaction ร่วมกัน แล้วให้ตัวส่งส่งต่อไปยัง broker แบบ durable หากไม่รองรับ ต้องออกแบบกลไกที่ทนทานเทียบเท่าก่อนใช้งานจริง การบันทึกแล้วส่ง event แยกกันไม่เพียงพอที่จะป้องกัน event สูญหาย
3. ให้แต่ละงานมี subscription หรือ queue ของตนเอง เพื่อให้ทั้งสามงานได้รับ event เดียวกัน ได้แก่ emailservice ที่เรียก MailFast แทน mock logic, loyaltyservice ที่ให้คะแนน และตัวประมวลผลที่บันทึก analytics “order placed” ตาม R-12 ข้อ 1–3
4. ใช้การส่งอย่างน้อยหนึ่งครั้ง พร้อมกลไก idempotency รายงาน เช่น order_id + action สำหรับคะแนน และ event_id สำหรับ analytics การบันทึกผลกับกุญแจป้องกันซ้ำต้องเป็น atomic ภายในขอบเขตของแต่ละงาน
5. ตรวจสอบการรองรับ idempotency และการค้นหาสถานะของ MailFast หาก timeout หลังส่งคำขอ อาจแยกไม่ได้ว่าส่งสำเร็จหรือไม่ จึงยังไม่รับประกันว่าอีเมลจะไม่ซ้ำ ต้องกำหนดนโยบายสำหรับกรณีนี้ก่อนใช้งาน
6. ให้ retry แบบมีระยะหน่วงและขีดจำกัด แยกงานที่ล้มเหลวต่อเนื่องไปยัง dead-letter queue พร้อมแจ้งเตือนและขั้นตอนตรวจสอบก่อน replay โดยคงกุญแจป้องกันงานซ้ำ
7. กำหนด schema และนโยบายเปลี่ยนรุ่นที่รองรับผู้รับเดิม ส่งข้อมูลเท่าที่จำเป็น และติดตามผลราย order_id และรายงานที่ต้องทำ ผลิตภัณฑ์ broker, protocol และที่เก็บ analytics ยังไม่ถูกเลือก

สำหรับ fraud scoring ในอนาคต หากต้องอนุมัติก่อนยอมรับคำสั่งซื้อ ต้องออกแบบขั้นตอนนั้นเพิ่มเติม การเพิ่มผู้รับ OrderPlaced อย่างเดียวไม่ตอบเงื่อนไขดังกล่าว

## Consequences

- **Positive:** เพิ่ม SMS หรือผู้รับใหม่ได้โดยคงผู้ส่งเดิมเมื่อ schema เพียงพอ (quality attribute: modifiability; เชื่อมกับ R-12 ย่อหน้าสุดท้าย)
- **Positive:** แยก retry และกำลังประมวลผล ทำให้ปลายทางหนึ่งล่มไม่จำเป็นต้องหยุดอีกสองงาน (quality attribute: availability, scalability; ผลที่คาดหวังจากข้อเสนอ)
- **Positive:** ไม่ต้องรอ MailFast และผู้รับอื่นเสร็จก่อนตอบรับ แต่ยังต้องรอการบันทึกคำสั่งซื้อและหลักฐาน event อย่างทนทาน (quality attribute: performance; ต้องวัดจริง)
- **Negative:** ผู้ใช้และทีมการตลาดอาจยังไม่เห็นผลทันทีหลังสั่งซื้อ (quality attribute: consistency, usability)
- **Negative:** เพิ่มค่าใช้จ่ายของ broker, outbox, สถานะงาน และการเฝ้าระวัง (quality attribute: cost, operability)
- **Risks and mitigations:** event อาจสูญหายในช่วงรอยต่อการบันทึกกับการส่ง จึงต้องตรวจสอบ atomicity และทดสอบการหยุดทำงานในช่วงนั้น (quality attribute: reliability)
- **Risks and mitigations:** retry หรือ replay อาจเพิ่มคะแนน ส่งอีเมล หรือบันทึก analytics ซ้ำ จึงต้องใช้ idempotency ตามงานและจัดการสถานะ MailFast ที่ไม่แน่นอน (quality attribute: correctness)
- **Risks and mitigations:** งานค้างอาจไม่ถูกสังเกต จึงต้องติดตามอายุงาน ความล้มเหลว และ dead-letter queue พร้อมผู้รับผิดชอบกู้คืน (quality attribute: observability, reliability)
- **Risks and mitigations:** ข้อมูลลูกค้าอาจกระจายเกินจำเป็น จึงต้องจำกัดข้อมูล สิทธิ์เข้าถึง และอายุเก็บตามนโยบายที่จะตกลง (quality attribute: security, privacy)

## Validation

- ทดสอบคำสั่งซื้อหนึ่งรายการว่ามีอีเมลผ่าน MailFast คะแนนผ่าน loyaltyservice และ analytics “order placed” ครบ โดยเชื่อมผลกลับถึงคำสั่งซื้อได้ ตาม R-12 ข้อ 1–3
- หยุดกระบวนการหลังบันทึกคำสั่งซื้อ ก่อนส่ง event และหลังส่งแต่ก่อนยืนยันการรับ เมื่อกู้คืนต้องไม่มีคำสั่งซื้อที่ยอมรับแล้วขาดงานโดยตรวจสอบไม่ได้
- ส่ง event ซ้ำและ replay ตรวจว่าคะแนนและ analytics ไม่ซ้ำ ทดสอบ MailFast timeout ทั้งก่อนและหลังผู้ให้บริการรับคำขอ แล้วตรวจผลตามนโยบายที่ตกลง
- จำลอง MailFast ใช้งานไม่ได้ ตรวจว่างานคะแนนและ analytics ยังดำเนินต่อได้ และงานอีเมลถูก retry หรือแสดงเป็นงานที่ต้องกู้คืน
- เพิ่มผู้รับงานจำลองโดยไม่แก้ผู้ส่งเมื่อ schema เพียงพอ และตรวจว่าผู้รับเดิมยังทำงานได้
- วัด latency การตอบรับ เวลาจนแต่ละงานสำเร็จ อายุงานค้าง และต้นทุนภายใต้ปริมาณงานที่ตกลง ยังไม่กำหนดตัวเลขผ่านเกณฑ์ เพราะ R-12 ไม่ได้ให้เป้าหมายไว้

## Open questions

- ใครเป็นผู้ตัดสินใจ ผู้ดูแลแต่ละงาน และผู้กู้คืนงานที่ล้มเหลว?
- งานใดต้องเสร็จก่อนตอบรับ ต้องเรียงลำดับหรือไม่ และล่าช้าได้เท่าใด?
- ระบบปัจจุบันยอมรับและบันทึกคำสั่งซื้อที่ใด ใช้ data store อะไร และรองรับ atomic outbox หรือกลไกเทียบเท่าหรือไม่?
- มีข้อจำกัดเรื่องโครงสร้างพื้นฐาน งบประมาณ ทักษะทีม และผลิตภัณฑ์ broker อย่างไร?
- MailFast ใช้ API และ authentication แบบใด มี rate limit, idempotency และการตรวจสถานะการส่งอย่างไร?
- สูตรให้คะแนน การคืนคะแนนเมื่อยกเลิก และตัวตนลูกค้าที่ใช้ผูกคะแนนคืออะไร?
- analytics ต้องเก็บที่ใด ใช้ schema ใด และทีมการตลาดต้องการความสดใหม่ระดับใด?
- ปริมาณคำสั่งซื้อ เป้าหมาย availability, latency, ระยะ retry และอายุเก็บ event/กุญแจป้องกันซ้ำคือเท่าใด?
- ยอมรับผลสำเร็จเพียงบางงานชั่วคราวได้หรือไม่ และจัดการคำสั่งซื้อยกเลิก งานตกค้าง หรืออีเมลที่สถานะไม่แน่นอนอย่างไร?
- มีข้อจำกัดด้านข้อมูลส่วนบุคคล สิทธิ์เข้าถึง การเก็บรักษา และข้อมูลที่ส่งให้ MailFast อย่างไร?
- fraud scoring ในปีหน้าต้องมีผลก่อนยอมรับคำสั่งซื้อหรือเป็นการวิเคราะห์ภายหลัง?
