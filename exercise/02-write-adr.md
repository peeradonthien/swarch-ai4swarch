# งานที่ 2: เขียน ADR สำหรับความต้องการใหม่ (ประมาณ 20 นาที)

> **เชื่อมโยงกับการบรรยาย:** T3 (GPT-4 แบบ zero-shot ให้ผลที่สอดคล้องกัน แต่ *ครบถ้วนน้อยกว่ามนุษย์* ส่วน few-shot ช่วยลดช่องว่างได้มาก), AICH3 (บริบท), สัปดาห์ที่ 10 (message broker)
> **คำถาม:** ADR ที่ AI เขียนดีขึ้นแค่ไหน เมื่อให้ตัวอย่างและบริบทจริงแก่ AI

อ่าน [สถานการณ์ (ภาษาไทย)](../docs/scenario.th.md) ก่อน: ความต้องการ **R-12** ว่าด้วยสิ่งที่เกิดขึ้นหลังจากลูกค้าสั่งซื้อสินค้า

ในแต่ละ run ให้เริ่ม **แชตหรือ session ใหม่** แล้วส่งข้อความด้านล่าง โดยแทนที่ `<paste R-12 here>` ด้วยข้อความ R-12 ภาษาอังกฤษที่อยู่ในกรอบอ้างอิงของ scenario

**Run a: ไม่มีตัวอย่าง (zero-shot)** → [`outputs/2a-adr.md`](outputs/2a-adr.md)
```
Follow prompts/2-write-adr.md
run: a
context: none
requirement: <paste R-12 here>
language: Thai
```

**Run b: มีตัวอย่าง + บริบท** → [`outputs/2b-adr.md`](outputs/2b-adr.md)
```
Follow prompts/2-write-adr.md
run: b
context: docs/scenario.md, docs/adr/0001-use-redis-for-cart-storage.md, system/online-boutique/src/checkoutservice/main.go
requirement: <paste R-12 here>
language: Thai
```

> บรรทัด `language: Thai` ทำให้ agent เขียน ADR เป็นภาษาไทย (หัวข้อของ template และชื่อทางเทคนิคยังคงเป็นภาษาอังกฤษ) หากต้องการภาษาอังกฤษให้ลบบรรทัดนี้ **ใช้ภาษาเดียวกันทั้ง Run a และ Run b** เพื่อให้เปรียบเทียบกันได้

> ใน Run a ให้ตรวจว่า agent ไม่ได้อ่านไฟล์อื่นนอกจาก template จริง ๆ หาก agent เปิด `docs/scenario.md` ให้บันทึกไว้ใน prompt log เพราะจะทำให้การเปรียบเทียบเปลี่ยนไป

## เปรียบเทียบ a กับ b

| เกณฑ์ | Run a | Run b |
|---|---|---|
| ใช้ตัวเลขจาก scenario หรือไม่ (latency, ช่วงพีก, ข้อจำกัดของ MailFast) | ไม่ได้ใช้ตัวเลข เพราะได้รับเพียง R-12 จึงไม่ทราบ p95 ≤ 500 ms, โหลด 200 orders/s หรือข้อจำกัด MailFast และเก็บเป้าหมายที่ยังไม่ทราบไว้ใน Open questions แทนการแต่งค่ามั่วๆ | ใช้ตัวเลขตรงกับ scenario: ปัจจุบันประมาณ 300 ms, เป้า p95 ≤ 500 ms, peak 200 orders/s, MailFast p95 1.5 s, p99 8 s, ผิดพลาดประมาณ 0.5%, จำกัด 50 emails/s เเละ คะแนนภายใน 1 นาที |
| ทางเลือกที่พิจารณา (ระบุ) | 1) เรียกทุกงานแบบ synchronous 2) asynchronous coordinator ที่เก็บสถานะ 3) durable message broker กระจาย OrderPlaced เลือกข้อ 3 เพื่อเพิ่มงานในอนาคต แต่ยังไม่เลือกผลิตภัณฑ์ broker | 1) synchronous calls จาก checkout 2) durable job store กับ worker ส่วนกลาง 3) order store + transactional outbox + RabbitMQ พร้อมคิวแยก เลือกข้อ 3 โดยอ้างภาระ MailFast ความยืดหยุ่น และประสบการณ์ RabbitMQ ของทีม |
| จัดการแต้มสะสมแบบ "ครั้งเดียวเท่านั้น" และ rate limit ของ MailFast หรือไม่ อย่างไร | เสนอ at-least-once delivery, idempotency แยกตามงาน และ atomic update ของผลกับกุญแจป้องกันซ้ำ แต่ยังไม่มีเกณฑ์คะแนนภายใน 1 นาที มีการถาม rate limit ของ MailFast ใน Open questions แทนการกำหนดค่าเอง | ระบุให้ loyaltyservice บันทึก order_id ที่ไม่ซ้ำและเพิ่มคะแนนใน transaction เดียวก่อน ACK, แยก exactly-once ของผลธุรกิจจากการส่งแบบ at-least-once และใช้ rate limiter รวมทุก replica/retry ที่ MailFast พร้อมคิวแยกเพื่อไม่ให้อีเมลหน่วงคะแนน แต่ยังต้องตกลงกรณี outage เกิน 1 นาที |
| มีสิ่งที่แต่งขึ้นเองหรือไม่ (ตัวเลข เครื่องมือ หรือข้อเท็จจริงที่ไม่มีใน scenario) | ไม่พบ | ไม่พบ |

## รับผิดชอบ ADR ฉบับสุดท้ายของตัวเอง

นิสิตคือสถาปนิก ให้คัดลอก `outputs/2b-adr.md` ไปที่ `docs/adr/0002-<short-title>.md` แล้วแก้ไข**ด้วยตัวเอง**จนพร้อมจะลงชื่อรับรอง ห้ามให้ agent ทำส่วนนี้

- แก้ไขสิ่งที่ผิดหรือแต่งขึ้นเอง และเพิ่มสิ่งที่ขาดหายไป
- ตัดสินใจขั้นสุดท้ายด้วยตัวเอง นิสิตสามารถไม่เห็นด้วยกับ AI ได้

นิสิตจะต้องปกป้อง ADR นี้ต่อหน้าคณะกรรมการรีวิวในส่วน B จึงต้องอธิบายทุกการตัดสินใจใน ADR ได้

| # | สิ่งที่เปลี่ยนจากร่างของ AI | เหตุผล |
|---|---|---|
| 1 | ระบุเงื่อนไขก่อนรับรองการออกแบบ และคงสถานะ `Proposed` | เลือกแนวทางแล้ว แต่ยังมีเรื่องการกู้คืนและข้อกำหนดที่ต้องตกลง |
| 2 | เพิ่มแผนรองรับคิวอีเมลค้าง | peak 200 orders/s แต่ MailFast ส่งได้ 50 emails/s; [Inferred] หากหนึ่งออเดอร์ส่งหนึ่งอีเมล คิวจะโตอย่างน้อย 150 รายการ/s การเพิ่ม worker แก้เพดานนี้ไม่ได้ |
| 3 | ตกลงเงื่อนไขคะแนนภายใน 1 นาทีเมื่อบริการล่ม | ถ้า `loyaltyservice` ล่มเกิน 1 นาที จะรับออเดอร์ต่อพร้อมรับประกันคะแนนทันเวลาทุกกรณีไม่ได้ |
| 4 | กำหนดวิธีกู้คืนช่วง payment/shipping ถึงการบันทึกออเดอร์ | อาจจ่ายเงินหรือจัดส่งสำเร็จแล้วระบบหยุดก่อนบันทึก outbox เเละ retry อาจทำงานซ้ำ เพราะ UUID ปัจจุบันถูกสร้างใหม่ทุก request |
| 5 | ทำหน่วย rate limit และการนับ retry ให้ชัด | scenario ระบุ 50 emails/s แต่ยังไม่บอกวิธีนับ API attempts หรือความสามารถป้องกันอีเมลซ้ำของ MailFast |
