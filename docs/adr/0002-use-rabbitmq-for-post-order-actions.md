# ADR-0002: ใช้ RabbitMQ แยกงานหลังสั่งซื้อออกจาก checkout

- **Status:** Proposed
- **Date:** 2026-10-27
- **Deciders:** Peeraodn

## Context and problem

R-12 ต้องส่งอีเมลผ่าน MailFast แทน mock `emailservice`, เพิ่มคะแนนผ่าน `loyaltyservice` ที่ต้องสร้าง และบันทึกเหตุการณ์สั่งซื้อให้การตลาด รวมถึงรองรับ SMS, fraud scoring และการปรับ recommendations ในปีถัดไป

| ประเด็น | หลักฐานและผลต่อการตัดสินใจ |
|---|---|
| เส้นทางปัจจุบัน | `PlaceOrder` เรียก `chargeCard` แล้ว `shipOrder` ก่อนสร้าง `OrderResult` และรอ `sendOrderConfirmation`; หากอีเมลผิดพลาดจะบันทึกคำเตือนและยังคืนผลสำเร็จ การส่งอีเมลใช้ gRPC `SendOrderConfirmation` |
| latency | p95 ของ `PlaceOrder` ต้อง ≤ 500 ms จากปัจจุบันประมาณ 300 ms ขณะที่ MailFast มี p95 1.5 s และ p99 8 s **[Inferred]** การรอ MailFast ในเส้นทางเดิมเสี่ยงเกินเป้าหมาย แต่ยังคำนวณ p95 รวมที่แน่นอนไม่ได้จาก quantile เหล่านี้ |
| ความจุอีเมล | โหลดสูงสุด 200 orders/s แต่ MailFast จำกัด 50 emails/s และผิดพลาดประมาณ 0.5% **[Inferred]** หากหนึ่งออเดอร์ใช้อีเมลหนึ่งครั้งและโหลดนี้ต่อเนื่อง คิวจะเพิ่มอย่างน้อย 150 รายการ/s ก่อนรวม retry; เพิ่ม worker อย่างเดียวแก้เพดานผู้ให้บริการไม่ได้ |
| คะแนนและความพร้อมใช้งาน | ต้องให้คะแนนภายใน 1 นาทีและ exactly once; ออเดอร์ต้องไม่ล้มเหลวเพราะอีเมล คะแนน หรือ analytics ใช้งานไม่ได้ |
| ทีมและการปฏิบัติการ | ทีม 4 คนถนัด Go/gRPC และ 2 คนเคยใช้ RabbitMQ; ระบบอยู่บน Kubernetes และองค์กรต้องการ open-source ที่ self-hosted |
| ช่องว่างด้านความทนทาน | `PlaceOrder` สร้าง UUID ใหม่ต่อการเรียก แล้วชำระเงิน จัดส่ง และตอบกลับ โดยไม่เห็นการบันทึกออเดอร์หรือ outbox ในฟังก์ชันนี้ กลไกเก็บออเดอร์ถาวรและกู้คืนงานของระบบทั้งหมด: **Not evidenced in the provided files** |

ADR-0001 เลือก Redis สำหรับตะกร้าซึ่งยอมรับการสูญหายได้เพราะยังไม่เกี่ยวกับเงิน **[Inferred]** เหตุผลนี้ไม่เพียงพอสำหรับใช้ตะกร้าเป็นหลักฐานถาวรของออเดอร์ที่ชำระเงินแล้ว

## Decision drivers

1. **Availability:** ความขัดข้องของงานหลังสั่งซื้อต้องไม่ทำให้ออเดอร์ล้มเหลว
2. **Correctness และ timeliness:** คะแนนต้องเพิ่มเพียงครั้งเดียวภายใน 1 นาที
3. **Performance และ scalability:** รักษา p95 ≤ 500 ms ที่ 200 orders/s พร้อมจัดการเพดานและความผิดพลาดของ MailFast
4. **Modifiability:** เพิ่มงานหลังสั่งซื้อในปีถัดไปได้โดยลดการแก้ `checkoutservice`
5. **Operability และ cost:** ให้ทีม 4 คนดูแลได้บน Kubernetes ตามทักษะและข้อจำกัด self-hosted

## Considered options

ทุกทางเลือกต่อไปนี้เป็นข้อเสนอสำหรับ R-12 ไม่ใช่คำอธิบายระบบที่มีอยู่

1. เรียก MailFast, `loyaltyservice` และตัวบันทึก analytics แบบ synchronous จาก `checkoutservice`
2. บันทึกงานอย่างทนทาน แล้วให้ worker ส่วนกลางจัดลำดับและเรียกบริการแต่ละตัวผ่าน API
3. บันทึกออเดอร์พร้อม transactional outbox แล้วกระจาย `OrderPlaced` ผ่าน RabbitMQ ไปยังคิวและ consumer แยกตามงาน

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| 1. เรียกแบบ synchronous | โครงสร้างใกล้โค้ดปัจจุบัน; ติดตามผลแต่ละการเรียกได้ตรงไปตรงมา | ต้องรอผู้ให้บริการที่ช้า; การขัดข้องกระทบเวลา checkout แม้กลืนข้อผิดพลาด; การ retry อย่างทนทานต้องเพิ่มกลไกอีก และทุกงานใหม่เพิ่ม coupling กับ checkout |
| 2. worker ส่วนกลางกับ durable job store | ตอบ checkout ก่อนทำงานภายนอกได้; รวมการ retry และติดตามสถานะไว้จุดเดียว; ไม่ต้องเพิ่ม message broker | ต้องสร้างการจองงาน การกู้คืน และสถานะรายงานย่อย; หากจัดลำดับร่วมกัน อีเมลค้างอาจหน่วงคะแนน; ทุกงานใหม่ต้องแก้ตัวประสานงาน |
| 3. RabbitMQ กับ outbox และคิวแยก | แยกความขัดข้องและ backlog ของแต่ละงาน; เพิ่ม consumer สำหรับงานใหม่ได้; สอดคล้องกับประสบการณ์ RabbitMQ ของสมาชิก 2 คน | เพิ่ม broker และ durable store ที่ต้องดูแล; มี eventual consistency, การส่งซ้ำ และความซับซ้อนในการติดตามเหตุการณ์; ต้องจัดการช่องว่างระหว่าง payment/shipping กับการบันทึกออเดอร์ |

## Decision

เลือก **ทางเลือก 3** เพื่อแยกเวลาทำงานของ MailFast และงานหลังสั่งซื้อออกจาก checkout และรองรับการเพิ่มงานตาม R-12 รายละเอียดต่อไปนี้เป็น **ข้อเสนอใหม่** ทั้งหมด:

1. **กำหนดจุดสำเร็จและบันทึกเหตุการณ์อย่างทนทาน:** หลัง payment และ shipping สำเร็จ ให้บันทึกสถานะออเดอร์ที่สำเร็จพร้อม outbox `OrderPlaced` ใน transaction เดียวของ durable store ก่อนตอบสำเร็จ แทนจุดเรียกอีเมลเดิม ให้ข้อมูลเหตุการณ์มี `event_id`, `order_id`, เวลาสั่งซื้อ, รุ่น schema และข้อมูลขั้นต่ำที่แต่ละงานต้องใช้ โดยไม่ส่งข้อมูลบัตรเครดิต เทคโนโลยีของ store และการกู้คืนยังต้องตัดสินใจตาม Open questions
2. **ส่งจาก outbox:** ให้ publisher ส่งเหตุการณ์เข้า RabbitMQ แล้วบันทึกว่าส่งสำเร็จเมื่อได้รับ publisher confirm; หากผลไม่แน่ชัดให้ส่งซ้ำด้วยตัวระบุเดิม กำหนด persistent messages, durable exchange และคิวแบบ replicated พร้อมการตรวจสอบ routing เพื่อให้ครบทุกงานที่บังคับทำ หาก broker ใช้งานไม่ได้ ให้เก็บงานไว้ใน outbox และส่งภายหลังโดยไม่รอ broker ในคำขอ checkout
3. **แยกคิวสำหรับทุกงาน:** ใช้ exchange กระจายสำเนาไปยังคิวอีเมล คิวคะแนน และคิว analytics แต่ละคิวมี consumer, retry และการติดตามแยกกัน เพิ่ม SMS หรืองานอื่นผ่านคิวใหม่เมื่อมี requirement ที่ชัดเจน ทุกงานต้องได้รับเหตุการณ์ของตนเอง ไม่แย่งรับจากคิวเดียวกัน
4. **แทนที่ mock emailservice:** ย้ายการส่งอีเมลไป consumer ที่เชื่อม MailFast และเลิกเรียก `SendOrderConfirmation` จากเส้นทาง `PlaceOrder` เดิม ข้อเท็จจริงคือ MailFast จำกัด **50 emails/s** ไม่ใช่ข้อยืนยันว่า API ทุกชนิดเรียกได้ 50 calls/s เสนอ rate limiter รวมทุก replica โดยนับการส่งครั้งแรกและ retry เข้างบเดียวกัน ภายใต้ **[Assumption]** ว่าหนึ่ง attempt ส่งหนึ่งอีเมล ให้จำกัด send attempts รวมไม่เกิน 50/s จนกว่าจะยืนยันสัญญา API และวิธีนับโควตา; หากข้อสมมติไม่ตรงต้องปรับก่อนใช้งาน ใช้ `order_id` เป็น idempotency key เฉพาะเมื่อผู้ให้บริการรองรับ และไม่รับประกันว่าอีเมลจะไม่ซ้ำเมื่อ timeout แล้วไม่ทราบผล
5. **ให้คะแนนครั้งเดียวที่ผลธุรกิจ:** ให้ consumer ของ `loyaltyservice` บันทึก `order_id` ที่ประมวลผลแล้วและเพิ่มคะแนนใน transaction เดียว โดยบังคับ uniqueness ตามออเดอร์ แล้วจึง ACK เหตุการณ์ การส่งซ้ำต้องคืนผลเดิมโดยไม่เพิ่มคะแนนอีก ข้อเสนอนี้ใช้การส่งแบบ at-least-once ร่วมกับ idempotent processing เพื่อให้ผลธุรกิจ exactly once ไม่ถือว่า broker ป้องกันข้อความซ้ำได้เอง
6. **บันทึก analytics และกู้คืนรายงานย่อย:** ตัวบันทึก analytics ต้องเก็บเหตุการณ์สำเร็จอย่างทนทานก่อน ACK และกำจัดรายการซ้ำด้วยตัวระบุเหตุการณ์ แต่ละ consumer ใช้ retry แบบหน่วงเวลาและ backoff; งานที่ยังแก้ไม่ได้เข้า dead-letter queue พร้อมแจ้งเตือนและ replay ด้วยตัวระบุเดิม จำนวน retry และเวลาหน่วงต้องกำหนดจากงบเวลาและผลทดสอบ

**ขอบเขตของการรับประกันและการกู้คืน:** transaction ของออเดอร์กับ outbox ไม่ครอบคลุม payment และ shipping; UUID ปัจจุบันถูกสร้างใหม่ทุกคำขอ และอาจเกิดช่องว่างหลังบริการภายนอกทำงานสำเร็จแต่ก่อน commit จึงเสนอเพิ่มขั้นตอนต่อไปนี้ก่อนอ้างความทนทานทั้งเส้นทาง:

- ก่อนเรียก payment/shipping ให้บันทึกออเดอร์สถานะรอดำเนินการและผูก stable checkout request key กับ `order_id` ใน durable store; client retry ของคำขอเดิมต้องใช้ key เดิม ไม่สร้างออเดอร์ใหม่ เทคโนโลยี store และวิธีส่ง key ยังต้องเลือก
- บันทึกผลที่ทราบของแต่ละขั้น พร้อม transaction ID และ tracking ID เมื่อมี หาก timeout หรือกู้คืนหลัง process หยุดแล้วไม่ทราบว่าปลายทางสำเร็จหรือไม่ ให้คงสถานะรอตรวจสอบและทำ reconciliation ห้ามเรียกซ้ำโดยถือว่ายังไม่เกิดผล การรองรับ idempotency และการค้นผลเดิมของปลายทางเป็น **Not evidenced in the provided files**
- เมื่อยืนยัน payment/shipping สำเร็จ ให้เปลี่ยนออเดอร์เป็นสำเร็จพร้อมสร้าง outbox ใน transaction เดียว แล้วจึงตอบสำเร็จ การกู้คืนต้องใช้ตัวระบุเดิมทั้งออเดอร์และ event เพื่อไม่สร้างงานหลังสั่งซื้อซ้ำ
- หากชำระเงินแล้วแต่จัดส่งหรือ commit ไม่สำเร็จ ต้องมีผู้รับผิดชอบตรวจและนโยบายกู้คืนหรือชดเชยที่ตกลงก่อนใช้งาน ขั้นตอนนี้ยังไม่ใช่หลักประกันว่า side effects ภายนอกเป็น exactly once

หาก durable store ใช้งานไม่ได้ การรับออเดอร์อย่างทนทานอาจหยุดชะงัก จึงเป็น dependency ใหม่ที่ต้องประเมิน availability ส่วนการหยุดของอีเมล คะแนน หรือ analytics ต้องไม่ถูกนำไปทำให้ออเดอร์ที่บันทึกสำเร็จแล้วล้มเหลว

### เงื่อนไขก่อนรับรองการออกแบบ

คงสถานะ **Proposed** จนกว่าจะมีข้อสรุปต่อไปนี้ โดยไม่ถือว่าการเลือก RabbitMQ เท่ากับผ่านข้อกำหนดแล้ว:

1. **คะแนนภายใน 1 นาทีขณะ outage:** ต้องตกลงวิธีประเมินกรณี `loyaltyservice` ล่มเกิน 1 นาทีแต่ระบบยังรับออเดอร์ ข้อกำหนดสองข้อนี้รับประกันพร้อมกันไม่ได้ในกรณีดังกล่าว จึงต้องบันทึกข้อขัดแย้งและข้อสรุปของผู้รับผิดชอบ ห้ามผ่อน requirement เองหรือถือว่า replay ภายหลังทำให้ทันกำหนดเดิม
2. **ความทนทานและการกู้คืน:** เลือก durable store, stable request key, ขอบเขต transaction และวิธี reconciliation ตามขั้นตอนข้างต้น พร้อมผลทดสอบช่วง payment/shipping ถึง outbox commit ก่อนรับรองว่าไม่มีออเดอร์ที่ตอบสำเร็จแล้วขาดงานหลังสั่งซื้อ
3. **ความจุและการปฏิบัติการ:** ยืนยันวิธีนับโควตา MailFast, ระยะ peak, ความล่าช้าอีเมลที่ยอมรับ, ความจุ outbox/คิว และผู้ดูแลการกู้คืน โดยประเมินภาระของ broker และ store กับทีม 4 คน

## Consequences

- **Positive:** checkout ไม่ต้องรอ MailFast หรือ consumer แต่ละตัว จึงลดการผูก latency และความพร้อมใช้งานเข้าด้วยกัน; ยังต้องวัดเวลาบันทึกออเดอร์/outbox จริง (quality attribute: performance, availability)
- **Positive:** คิวคะแนนไม่ติดตาม backlog อีเมล และเพิ่มงานใหม่ผ่าน consumer ได้ (quality attribute: scalability, modifiability)
- **Negative:** ผลอีเมล คะแนน และ analytics เกิดภายหลังการตอบ checkout; เพิ่ม broker, durable store, dashboard และภาระกู้คืนให้ทีม 4 คน (quality attribute: consistency, operability, cost)
- **Risks and mitigations:** เหตุการณ์ซ้ำอาจเพิ่มคะแนนซ้ำ จึงต้องใช้ uniqueness และ transaction ภายใน `loyaltyservice` รวมถึงทดสอบการหยุดก่อน ACK (quality attribute: correctness)
- **Risks and mitigations:** MailFast ระบายงานไม่ทันโหลดสูงสุด จึงต้องวัดอายุและขนาดคิว วางแผนพื้นที่เก็บ และตกลงความล่าช้าหรือเพิ่มโควตากับผู้ให้บริการ; retry ต้องใช้โควตาร่วมด้วย (quality attribute: capacity, timeliness, cost)
- **Risks and mitigations:** outbox, broker หรือ consumer ขัดข้องอาจทำให้คะแนนเกิน 1 นาที จึงติดตามเวลาตั้งแต่สั่งซื้อถึงเพิ่มคะแนน พร้อมแจ้งเตือนก่อนพ้นกำหนดและมีขั้นตอนกู้คืน; replication เพียงอย่างเดียวไม่รับประกันกำหนดเวลา (quality attribute: availability, timeliness)
- **Risks and mitigations:** process หยุดระหว่าง payment/shipping กับการบันทึกออเดอร์อาจทำให้งานตกหล่นหรือเกิดการทำซ้ำ ต้องออกแบบ reconciliation และ idempotency ของ checkout; จำกัดข้อมูลส่วนบุคคลใน event และสิทธิ์เข้าถึงแต่ละคิว (quality attribute: durability, correctness, security)

### แผนรองรับคิวอีเมลค้าง

**[Inferred]** ภายใต้สมมติฐานหนึ่งออเดอร์ส่งหนึ่งอีเมล เมื่อโหลดคงที่ 200 orders/s แต่ส่งได้ไม่เกิน 50 emails/s คิวจะโตอย่างน้อย 150 รายการ/s หาก peak นาน `T` วินาที จะสะสมอย่างน้อย `150T` รายการ และถ้าหลัง peak ไม่มีงานใหม่และส่งสำเร็จได้เต็ม 50 emails/s จะใช้เวลาระบายอย่างน้อย `3T` วินาที; retry และ outage อาจทำให้นานขึ้น ตัวเลขนี้เป็นการคำนวณจาก scenario ไม่ใช่ผลทดสอบหรือข้อสมมติว่า peak มีระยะเวลาที่ทราบแล้ว

- กำหนดความจุจากระยะ peak และโหลดหลัง peak ที่ได้รับคำตอบ ไม่ใช้การเพิ่ม worker เป็นวิธีแก้โควตาของ MailFast
- ติดตามจำนวนงานค้าง อายุอีเมลเก่าสุด พื้นที่เก็บ อัตราส่งสำเร็จ และ retry พร้อมกำหนดผู้รับผิดชอบและเกณฑ์แจ้งเตือนก่อนพื้นที่เต็ม
- ถ้าเวลาระบายไม่ตรงความต้องการ ต้องตกลงความล่าช้าหรือเพิ่มโควตา MailFast ก่อนใช้งาน ไม่อ้างว่าคิวมีความจุไม่จำกัด (quality attribute: capacity, timeliness, cost; ข้อเสนอใหม่)

## Validation

แผนต่อไปนี้เป็นเกณฑ์ตรวจสอบข้อเสนอ ยังไม่ได้ดำเนินการทดสอบ:

- ทดสอบโหลด 200 orders/s พร้อมจำลอง latency และความผิดพลาดของ MailFast ตาม scenario; วัด p95 `PlaceOrder` ให้ ≤ 500 ms และอัตราส่งอีเมลให้อยู่ใน 50 emails/s ตามวิธีนับโควตาที่ผู้ให้บริการยืนยัน รวมการตรวจ send attempts/retry ตามนโยบาย limiter ที่เลือก เก็บเวลาจริงโดยไม่บวก p95 ของแต่ละบริการเข้าด้วยกัน
- กรณีทำงานปกติ: วัดตั้งแต่จุดที่ถือว่าออเดอร์สำเร็จจนคะแนน commit ให้ไม่เกิน 1 นาทีทุกออเดอร์ ไม่ใช้เพียงค่าเฉลี่ย; ตรวจยอดคะแนนไม่ให้ขาดหรือซ้ำ การผ่านกรณีนี้อย่างเดียวไม่พิสูจน์ว่าผ่านเงื่อนไข outage
- ส่งเหตุการณ์ซ้ำและ replay จาก dead-letter queue; หยุด `loyaltyservice` หลัง commit แต่ก่อน ACK แล้วตรวจว่าคะแนนเพิ่มครั้งเดียว ตรวจ analytics ไม่ขาดและไม่ซ้ำด้วยตัวระบุเดิม
- กรณี outage: ปิด MailFast, `loyaltyservice` และ analytics ทีละตัวและพร้อมกัน ตรวจว่าออเดอร์ยังสำเร็จและงานกลับมาทำครบหลังเปิดบริการ แยกทดสอบ outage สั้นกับกรณีเกิน 1 นาที และรายงานคะแนนที่เกินกำหนดเป็นการละเมิดเป้าเดิม ไม่เปลี่ยนให้เป็นผลผ่านเพียงเพราะกู้คืนได้ ต้องใช้ข้อสรุปของผู้รับผิดชอบในการตัดสินรับรอง
- หยุด broker และ publisher; ทดสอบการหยุดหลัง publish แต่ก่อนบันทึกสถานะ outbox และการเริ่มใหม่ ตรวจออเดอร์ที่ตอบสำเร็จเทียบกับเหตุการณ์และผลของทั้งสามงานทุกตัว
- ทดสอบการหยุดหลัง payment, หลัง shipping และก่อน/หลัง commit ของออเดอร์/outbox พร้อม client retry ด้วย key เดิม ตรวจว่าใช้ `order_id` เดิม, ไม่เรียก side effects ที่ผลยังไม่ทราบซ้ำแบบอัตโนมัติ และตรวจสอบผลค้างได้; ออเดอร์ที่ตอบสำเร็จต้องมี outbox ที่ตามไปถึงงานทั้งสามได้ ต้องทดสอบ reconciliation กับความสามารถจริงของปลายทางก่อนอ้างความทนทานทั้งเส้นทาง
- วัด backlog อีเมล พื้นที่เก็บ และเวลาระบายคิวตามระยะเวลาโหลดสูงสุดที่ได้รับคำตอบแล้ว พร้อมตรวจว่า backlog นี้ไม่ทำให้คิวคะแนนพ้น 1 นาที
